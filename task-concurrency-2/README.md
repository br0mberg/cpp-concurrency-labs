## Описание задания

Нужно подсчитать количество вхождений каждого байта (0-255) в огромном массиве данных
(100 млн элементов). Это классическая задача построения **гистограммы**.

Вам предоставлен файл `histogram.cpp` — однопоточная (sequential) реализация, которая
служит базовым замером и эталоном корректности. Также дан заголовочный файл `common.h`
с функциями генерации данных и проверки результата.

Ваша задача — написать **три параллельные версии** подсчёта гистограммы, используя
разные подходы к синхронизации, и сравнить их производительность.

Каждая программа принимает опциональный аргумент — размер массива (по умолчанию 100 000 000).

**Не модифицируйте** файлы `histogram.cpp` и `common.h`.

## Сборка проекта

Проект собирается через **CMake**. В `CMakeLists.txt` уже настроен таргет для
`histogram`. Таргеты для ваших решений закомментированы — раскомментируйте их
после создания соответствующих файлов.

```bash
mkdir build && cd build
cmake ..
cmake --build .
```

После сборки бинарники окажутся в папке `build/`.

## Общие требования

- Каждый файл-решение должен быть **самодостаточным** — полная программа с `main()`.
- Используйте `common.h` для генерации данных (`generate_data`) и проверки
  (`histogram_sequential`, `verify`).
- Количество потоков: используйте `std::thread::hardware_concurrency()`, но
  ограничьте диапазоном 4-8 потоков.
- Каждая программа должна завершаться за разумное время (mutex-версия будет медленной,
  это нормально — но она должна завершиться).
- **Не пушьте** папку `build/` — она уже в `.gitignore`.

### Формат вывода

Каждая программа должна выводить ровно четыре строки:

```
Method: <имя_метода>
Threads: <количество_потоков>
Time: <время_в_мс> ms
Correct: true
```

Где `<имя_метода>` — `mutex`, `atomic` или `local` соответственно.

Значение `Correct: true` означает, что параллельная гистограмма совпала
с эталонной однопоточной. Используйте функцию `verify()` из `common.h`.

## Часть 1. Глобальный Mutex

*Стоимость: 3 балла*

Создайте файл `histogram_mutex.cpp`.

Подход: один `std::vector<int> counts(256)` защищён одним глобальным `std::mutex`.
Каждый поток при каждом инкременте счётчика захватывает мьютекс.

**Ожидание**: катастрофически медленно. Мьютекс захватывается 100 млн раз.

Проверка:

```bash
cd build
./histogram_mutex
# Ожидаемый вывод: Correct: true
```

### Требования к решению

- Файл **должен содержать** `mutex`.
- Файл **не должен содержать** `atomic` (это подход Части 2).
- В `CMakeLists.txt` должен быть раскомментирован таргет `histogram_mutex`.
- Вывод должен содержать `Correct: true`.

## Часть 2. Глобальные атомики

*Стоимость: 3 балла*

Создайте файл `histogram_atomic.cpp`.

Подход: используйте `std::vector<std::atomic<int>> counts(256)`. Атомарные операции обеспечивают корректность.


**Ожидание**: быстрее, чем mutex, но всё равно медленно из-за трафика
когерентности кеша (cache coherence traffic) — потоки пишут в одни и те же
кеш-линии.

Проверка:

```bash
cd build
./histogram_atomic
# Ожидаемый вывод: Correct: true
```

### Требования к решению

- Файл **должен содержать** `atomic`.
- Файл **не должен содержать** `mutex` (это подход без блокировок).
- В `CMakeLists.txt` должен быть раскомментирован таргет `histogram_atomic`.
- Вывод должен содержать `Correct: true`.

## Часть 3. Локальные счётчики (Best Practice)

*Стоимость: 4 балла*

Создайте файл `histogram_local.cpp`.

Подход: каждый поток создаёт свой **локальный** `std::vector<int> local_counts(256)`.
Во время подсчёта потоки работают полностью независимо. Результат складывается в глобальный вектор.


**Ожидание**: самый быстрый вариант. Потоки не мешают друг другу во время
основной работы.

Проверка:

```bash
cd build
./histogram_local
# Ожидаемый вывод: Correct: true
```

### Требования к решению

- Файл **не должен содержать** `atomic` (это подход без атомиков).
- Файл **должен содержать** `thread` (многопоточный).
- В `CMakeLists.txt` должен быть раскомментирован таргет `histogram_local`.
- Вывод должен содержать `Correct: true`.

## Вопрос на засыпку

Почему вариант 3 (локальные счётчики) оказался быстрее варианта 2 (атомики),
хотя атомарные операции считаются "быстрыми"?

Подсказка: подумайте о том, что происходит на уровне **кеш-линий** процессора,
когда несколько ядер одновременно модифицируют соседние ячейки памяти.
Изучите термины: *cache coherence*, *MESI protocol*, *false sharing*.

## post scriptum

Главный инсайт этого задания — **не всё, что lock-free, быстрее, чем с блокировками**.
Атомики убирают ожидание на мьютексе, но не убирают трафик когерентности кеша.
Когда 8 ядер одновременно модифицируют соседние `atomic<int>` в одном массиве,
протокол MESI заставляет кеш-линии "прыгать" между ядрами на каждой записи.
Локальные счётчики решают проблему в корне: каждое ядро пишет в свою память,
а объединение происходит один раз в конце. Удачи!
